# enclave/

> The BLS signing binary that runs **inside** an AWS Nitro Enclave, so the plaintext key never touches the host.

## What this is
A separate Go module (`github.com/ava-labs/avalanche-deploy/tools/remote-signer/enclave`, own `go.mod` with `replace ... => ../`) that builds the program packaged into the enclave image. It is its own module because it has a distinct dependency set (AWS SDK, `mdlayher/vsock`, `blst`) and is cross-compiled/statically linked independently of the host signer. It is the enclave half of the `awsnitro` backend: the host (`api/awsnitro`) launches it and talks to it over vsock; this binary decrypts the BLS key via KMS and serves signatures.

## Contents
- `main.go` — the full enclave program: vsock init handshake, KMS decrypt, BLS sign/PoP server.
- `Dockerfile` — Alpine 3.21 image that bakes in the prebuilt static binary, the encrypted key blob, and the KMS key ID; build instructions live in the header comments.
- `go.mod` / `go.sum` — module definition (replaces the root module with `../`).

## How it works
Wire protocol and ports come from `internal/enclaveproto`. Startup sequence (see `main.go`):
1. Listen on vsock `VSockInitPort` (5001) for the host's `InitMessage`, which carries temporary AWS credentials (the enclave has no IMDS) plus region. `receiveInit` loops past empty/probe connections until it decodes a real message.
2. Build a KMS client whose HTTP transport dials the host's vsock-proxy at CID `3`, port `8443` (forwarded to `kms.<region>.amazonaws.com:443`); call `Decrypt` on the ciphertext read from the path in `os.Args[1]`, using the KMS key ID read from `/kms-key-id.txt`. Plaintext must be a 32-byte scalar.
3. Deserialize the `blst.SecretKey`, derive the compressed G1 public key, and return it hex-encoded as the `InitResponse` on the same init connection.
4. Serve on vsock `VSockPort` (5000): `public_key`, `sign` (DST `...RO_POP_`), and `sign_pop` (DST `...RO_POP_`) requests, one JSON request/response per connection. The DSTs are hardcoded here and must match AvalancheGo — see `tests/`.

## Build & run
These are the steps from `Dockerfile`; run on the EC2 host (Amazon Linux). The binary **must** be statically linked.
```sh
cd enclave
sudo dnf install -y glibc-static
CGO_ENABLED=1 go build -ldflags '-linkmode external -extldflags "-static"' -o enclave-bin .
file enclave-bin            # must say "statically linked"
cp ~/bls.key.enc ./bls.key.enc
docker build -f Dockerfile -t remote-signer-enclave --build-arg KMS_KEY_ID=<arn> .
docker run --rm remote-signer-enclave /enclave-bin   # smoke test: prints "usage: enclave <encrypted-key-path>"
nitro-cli build-enclave --docker-uri remote-signer-enclave --output-file remote-signer.eif
nitro-cli run-enclave --eif-path remote-signer.eif --cpu-count 2 --memory 512 --enclave-cid 16
```

## Troubleshooting
- **Host signer times out dialing vsock init port 5001 / enclave dies silently** → the binary is dynamically linked (glibc) but the image is Alpine/musl, so it cannot exec inside the enclave. → Rebuild with `-linkmode external -extldflags "-static"` and confirm with `file enclave-bin`.
- **`KMS decrypt` error in enclave logs** → vsock-proxy not running on the host, wrong region, IAM denies `kms:Decrypt`, or the key policy has a `kms:RecipientAttestation:*` condition — the enclave sends **no** attestation document, so such a condition always denies (see `docs/aws-nitro.md`). → Start `vsock-proxy` (port 8443), check the instance role, remove any attestation condition.
- **`invalid BLS scalar` / `expected 32-byte BLS scalar`** → the ciphertext blob isn't a 32-byte BLS key (wrong file or generated by a different tool). → Regenerate with `keytool` and re-copy `bls.key.enc`.
- **`usage: enclave <encrypted-key-path>`** → started with no path argument. `main.go` reads only `os.Args[1]` (the key path); the KMS key ID always comes from `/kms-key-id.txt` baked in at image build time (the build fails if `--build-arg KMS_KEY_ID` is missing).
